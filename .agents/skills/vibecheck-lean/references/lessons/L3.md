# L3 · Code with branches

> Real code is full of `if`: guards, limits, validation. Each branch is a separate situation, and a proof has to cover every one of them. Lean won't let you skip any, and the skipped branches are where bugs hide.

*About 10 minutes · practice file `Learn/L3_Branches.lean`*

## Read it piece by piece

```lean
def clamp (lo hi x : Int) : Int :=
  if x < lo then lo else if x > hi then hi else x

#eval clamp 0 10 15     -- 10
#eval clamp 0 10 (-3)   -- 0
```

```tree spans=4:9,10:25
def clamp (lo hi x : Int) : Int :=
    │     └─ three inputs, all `Int`: integers, may be negative
    └─ keep `x` between `lo` and `hi`
```

```tree spans=2:4,5:11,12:19,20:42,43:49
  if x < lo then lo else if x > hi then hi else x
  │  │      │       │                      └─ otherwise, `x` unchanged
  │  │      │       └─ otherwise, a second choice
  │  │      └─ the result when it holds
  │  └─ the condition
  └─ a choice
```

A negative number as an argument needs parentheses, `(-3)`, so Lean doesn't read it as subtraction.

## The claim, and its assumption

```lean
theorem clamp_ge (lo hi x : Int) (h : lo ≤ hi) : lo ≤ clamp lo hi x := by
  unfold clamp
  split <;> (try split) <;> omega
```

```tree spans=17:32,33:46,49:67
theorem clamp_ge (lo hi x : Int) (h : lo ≤ hi) : lo ≤ clamp lo hi x := by
                 │               │               └─ the result never drops below `lo`
                 │               └─ …where `lo ≤ hi`: an assumption, named `h`
                 └─ for any three integers…
```

The theorem only promises something to callers who pass `lo ≤ hi`. Inside the proof, `h` is that promise, available to use.

## One goal per branch

After `unfold clamp` and `split`, the panel shows two goals, one for each branch of the first `if`:

```goal
case isTrue
lo hi x : Int
h : lo ≤ hi
h✝ : x < lo
⊢ lo ≤ lo
```

```goal
case isFalse
lo hi x : Int
h : lo ≤ hi
h✝ : ¬x < lo
⊢ lo ≤ if x > hi then hi else x
```

Each branch gets what it knows: `x < lo` in one, its opposite `¬x < lo` in the other (`¬` means "not"). The `✝` marks a name Lean chose; tactics can use the fact, but you can't type its name. The second goal still contains an `if`, so it needs one more split.

```tree spans=2:7,8:11,12:23,28:33
  split <;> (try split) <;> omega
  │     │   │               └─ finish each case
  │     │   └─ split again where there's another `if`; skip quietly where not
  │     └─ do the next step to every goal just made
  └─ one goal per branch of the first `if`
```

**`grind`** does the case splits and the arithmetic in one go. It's often the first thing to try:

```lean
example (lo hi x : Int) (h : lo ≤ hi) : lo ≤ clamp lo hi x := by
  unfold clamp
  grind
```

## Results that might be missing

```lean
def withdraw (bal amt : Nat) : Option Nat :=
  if amt ≤ bal then some (bal - amt) else none

#eval withdraw 100 30   -- some 70
#eval withdraw 10 30    -- none
```

```tree spans=4:12,31:41
def withdraw (bal amt : Nat) : Option Nat :=
    │                          └─ a result that may be missing: `some n` or `none`
    └─ take `amt` out of a balance `bal`
```

A property worth having: whatever comes back is never more than the balance.

```lean
theorem withdraw_le (bal amt r : Nat) (h : withdraw bal amt = some r) : r ≤ bal := by
  unfold withdraw at h
  split at h <;> grind
```

```tree spans=2:12,13:16,17:22
  split at h <;> grind
  │          │   └─ …apply grind: logic, arithmetic, and `none ≠ some r`
  │          └─ to every case…
  └─ case on the `if` inside `h`
```

```goal
case isTrue
bal amt r : Nat
h✝ : amt ≤ bal
h : some (bal - amt) = some r
⊢ r ≤ bal
```

```goal
case isFalse
bal amt r : Nat
h✝ : ¬amt ≤ bal
h : none = some r
⊢ r ≤ bal
```

The second case can't happen: `none` is never `some r`, so `h` is a contradiction and `grind` closes the goal on that alone. Impossible branches are free.

## When the claim is wrong

```lean fails
theorem clamp_le_bad (lo hi x : Int) : clamp lo hi x ≤ hi := by
  unfold clamp
  grind
-- Lean says: `grind` failed
-- Without the assumption `lo ≤ hi` this is false, and Lean won't prove it. A failing proof is often a bug report about the claim.
```

```lean
#eval clamp 5 1 3   -- 5
```

With `lo = 5` and `hi = 1`, clamp returns 5, which is not `≤ 1`. When a proof won't close, try small inputs with `#eval`. You'll often find a counterexample, and the fix is an assumption you forgot to state.

## Rule of thumb

| The code has | Do |
| --- | --- |
| an `if` or `match` in the goal | `split`, or let `grind` do it |
| an `if` inside a hypothesis `h` | `split at h` |
| an `Option` result | case on `some` and `none`; impossible cases close themselves |
| a proof that won't close | look for a missing assumption; test small values with `#eval` |

## Check yourself

1. After `split`, what new fact appears in each branch?
   Answer: The condition: `x < lo` in one branch, `¬x < lo` in the other.
2. What does `<;>` do?
   Answer: It runs the next tactic on every goal the previous one produced.
3. Why did `clamp_le_bad` fail?
   Answer: It's false without `lo ≤ hi`: `clamp 5 1 3 = 5`.
