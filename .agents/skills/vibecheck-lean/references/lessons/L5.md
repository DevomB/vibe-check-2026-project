# L5 · Fast code equals simple code

> This is the pattern you'll use most on real code. Write a slow version that is obviously right, write the fast version you actually ship, and prove they always agree. Every property of the simple one then carries over to the fast one.

*About 15 minutes · practice file `Learn/L5_Reference.lean`*

## Two ways to count

```lean
def lenAcc : Nat → List α → Nat
  | acc, [] => acc
  | acc, _ :: xs => lenAcc (acc + 1) xs

def lenFast (xs : List α) : Nat := lenAcc 0 xs

#eval lenFast [5, 6, 7]   -- 3
```

```tree spans=13:18,19:27,28:31
def lenAcc : Nat → List α → Nat
             │     │        └─ …give back a number
             │     └─ …and a list…
             └─ a running count, the accumulator `acc`…
```

```tree spans=4:16,20:39
  | acc, _ :: xs => lenAcc (acc + 1) xs
    │               └─ count one, carry on with the rest
    └─ both arguments, matched together
```

```text
lenAcc 0 [5, 6, 7]
→ lenAcc 1 [6, 7]
→ lenAcc 2 [7]
→ lenAcc 3 []
→ 3
```

The reference is the library's `List.length`, defined like L4's `len`. `lenAcc` carries its answer along instead of leaving `1 + …` waiting on the stack, so it runs on huge lists without growing the stack. Is it always the same as `List.length`?

## The trick: prove more than you need

You want `lenAcc 0 xs = xs.length`. That doesn't work by induction directly, because the recursive call starts from `1`, not `0`. So prove it for every starting accumulator:

```lean
theorem lenAcc_eq (acc : Nat) (xs : List α) : lenAcc acc xs = acc + xs.length := by
  induction xs generalizing acc with
  | nil => simp [lenAcc]
  | cons x xs ih => simp [lenAcc, ih]; omega
```

```tree spans=2:14,15:31
  induction xs generalizing acc with
  │            └─ keep `acc` open: the hypothesis will hold for every `acc`
  └─ induction on the list, as in L4
```

```goal
case cons
α : Type u_1
x : α
xs : List α
ih : ∀ (acc : Nat), lenAcc acc xs = acc + xs.length
acc : Nat
⊢ lenAcc acc (x :: xs) = acc + (x :: xs).length
```

Read `ih` closely. `∀ (acc : Nat)` means "for every `acc`". One step of `lenAcc` turns the goal into a statement about `lenAcc (acc + 1) xs`, and `ih` covers it, because it holds for every accumulator, `acc + 1` included.

The headline theorem is then one line:

```lean
theorem lenFast_correct (xs : List α) : lenFast xs = xs.length := by
  simp [lenFast, lenAcc_eq]
```

## Where it stops working

```lean fails
theorem lenAcc_eq' (acc : Nat) (xs : List α) : lenAcc acc xs = acc + xs.length := by
  induction xs with
  | nil => simp [lenAcc]
  | cons x xs ih => simp [lenAcc, ih]; omega
-- Lean says: omega could not prove the goal
-- Without `generalizing acc`, ih is about this one acc only: `lenAcc acc xs = acc + xs.length`. The goal needs `lenAcc (acc + 1) xs`, and ih says nothing about that.
```

## Rule of thumb

When a recursive call changes an argument (an accumulator, a counter, a position, a stack), add `generalizing` and that argument to `induction`. If you're stuck on a goal that looks almost like `ih` but not quite, this is usually why.

## Check yourself

1. Why can't you prove `lenAcc 0 xs = xs.length` by induction as it stands?
   Answer: The recursive call uses accumulator 1, not 0, so a hypothesis about 0 doesn't apply.
2. What does `∀ (acc : Nat)` in `ih` mean?
   Answer: The hypothesis holds for every accumulator value, so it can be used for `acc + 1`.
3. Once `lenFast_correct` is proved, what do you know about `lenFast`?
   Answer: Everything you know about `List.length`, because they're equal on every input.
