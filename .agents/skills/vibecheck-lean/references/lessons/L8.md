# L8 · A verified compiler

> The capstone. You'll define a tiny language, give it a meaning, compile it to a stack machine, and prove the compiled code always computes the same answer. Query planners, interpreters and code generators all have this shape.

*About 20 minutes · practice file `Learn/L8_Compiler.lean`*

## A language as a type

```lean
inductive Expr where
  | num : Nat → Expr
  | add : Expr → Expr → Expr
  | mul : Expr → Expr → Expr
```

```tree spans=0:9,10:14
inductive Expr where
│         └─ the name: an arithmetic expression
└─ a type defined by listing its shapes
```

```tree spans=4:7,10:20
  | num : Nat → Expr
    │     └─ …give it a number, get an expression
    └─ shape 1: a literal…
```

```tree spans=4:7,10:28
  | add : Expr → Expr → Expr
    │     └─ …of two expressions, so expressions nest
    └─ shape 2: a sum…
```

`2 + 3 * 4` is this tree, written `.add (.num 2) (.mul (.num 3) (.num 4))`:

```text
        add
       /   \
   num 2    mul
           /   \
       num 3    num 4
```

## What an expression means

```lean
def Expr.eval : Expr → Nat
  | .num n => n
  | .add a b => a.eval + b.eval
  | .mul a b => a.eval * b.eval
```

```tree spans=4:12,16:31
  | .add a b => a.eval + b.eval
    │           └─ evaluate each subtree, then add: recursion on a tree
    └─ an `add` node with subtrees `a` and `b`
```

The leading dot in `.add` means "the `add` that fits here", so you don't have to write `Expr.add`.

## A machine and a compiler

```lean
inductive Instr where
  | push : Nat → Instr
  | add
  | mul

def exec : List Instr → List Nat → List Nat
  | [], s => s
  | .push n :: is, s => exec is (n :: s)
  | .add :: is, b :: a :: s => exec is ((a + b) :: s)
  | .mul :: is, b :: a :: s => exec is ((a * b) :: s)
  | _ :: is, s => exec is s

def compile : Expr → List Instr
  | .num n => [.push n]
  | .add a b => compile a ++ compile b ++ [.add]
  | .mul a b => compile a ++ compile b ++ [.mul]

#eval exec (compile (.add (.num 2) (.mul (.num 3) (.num 4)))) []   -- [14]
#eval (Expr.add (.num 2) (.mul (.num 3) (.num 4))).eval   -- 14
```

```tree spans=4:14,16:27,31:53
  | .add :: is, b :: a :: s => exec is ((a + b) :: s)
    │           │              └─ pop both, push their sum, carry on
    │           └─ the stack has two numbers on top
    └─ the next instruction is `add`; the rest is `is`
```

```tree spans=4:14,18:27
  | _ :: is, s => exec is s
    │             └─ skip the instruction
    └─ anything else, such as a stack too short to add
```

The machine running the compiled `2 + 3 * 4`:

```text
instruction    stack (top first)
push 2         [2]
push 3         [3, 2]
push 4         [4, 3, 2]
mul            [12, 2]
add            [14]
```

Two `#eval`s agreeing on one input is a test. The goal of this level is a proof that they agree on every expression.

## Induction on a tree

An `Expr` has three shapes, so induction has three cases. `add` and `mul` each get two hypotheses, one per subtree. A warm-up: compiled code has one instruction per node of the tree.

```lean
def Expr.size : Expr → Nat
  | .num _ => 1
  | .add a b => a.size + b.size + 1
  | .mul a b => a.size + b.size + 1

theorem compile_length (e : Expr) : (compile e).length = e.size := by
  induction e with
  | num n => simp [compile, Expr.size]
  | add a b iha ihb => simp [compile, Expr.size, iha, ihb]; omega
  | mul a b iha ihb => simp [compile, Expr.size, iha, ihb]; omega
```

```tree spans=4:11,12:19,23:58,60:65
  | add a b iha ihb => simp [compile, Expr.size, iha, ihb]; omega
    │       │          │                                    └─ tidy the arithmetic
    │       │          └─ unfold one step, rewrite with both
    │       └─ two hypotheses: the fact holds for `a`, and for `b`
    └─ case: the tree is `add a b`
```

```goal
case add
a b : Expr
iha : (compile a).length = a.size
ihb : (compile b).length = b.size
⊢ (compile (a.add b)).length = (a.add b).size
```

## Generalize over what the machine changes

As `exec` runs, two things change: the instructions left and the stack. A lemma about `exec` has to hold for any remaining instructions and any stack, just like L5's accumulator. Here is that idea on a simpler program, which pushes a list of numbers:

```lean
def pushAll (ns : List Nat) : List Instr := ns.map .push

theorem exec_pushAll (ns : List Nat) (rest : List Instr) (s : List Nat) :
    exec (pushAll ns ++ rest) s = exec rest (ns.reverse ++ s) := by
  induction ns generalizing s with
  | nil => simp [pushAll]
  | cons n ns ih => simp [pushAll] at *; simp [exec, ih]
```

```tree spans=10:28,30:31,34:61
    exec (pushAll ns ++ rest) s = exec rest (ns.reverse ++ s) := by
          │                   │   └─ same as running `rest` with the numbers already pushed
          │                   └─ from any starting stack
          └─ the pushes, followed by any program `rest`
```

`ns.map .push` turns each number into a `push` instruction. `simp [pushAll] at *` simplifies everywhere, the hypothesis `ih` included.

```lean fails
theorem exec_pushAll' (ns : List Nat) (rest : List Instr) (s : List Nat) :
    exec (pushAll ns ++ rest) s = exec rest (ns.reverse ++ s) := by
  induction ns with
  | nil => simp [pushAll]
  | cons n ns ih => simp [pushAll] at *; simp [exec, ih]
-- Lean says: unsolved goals
-- After pushing n the stack is n :: s, but ih only speaks about the original stack s. `generalizing s` fixes it.
```

## Rule of thumb

1. A type defined with `inductive` means `induction` on it: one case per shape, one hypothesis per subtree.
2. For a machine like `exec`, state the lemma for any remaining program and any stack, and generalize over everything the machine changes.
3. Prove the general lemma first, then get the headline theorem from it, as in L5.

## Check yourself

1. How many induction hypotheses does the `add` case get, and why?
   Answer: Two, one for each subtree.
2. Why does `exec_pushAll` need `generalizing s`?
   Answer: Each push changes the stack, so the hypothesis has to hold for any stack.
3. What's the difference between the two `#eval`s agreeing and a proof?
   Answer: The `#eval`s check one expression; the proof covers every expression.
